# Database Baseline v2

## Goal

Replace the historical migration-shaped consolidated schemas with one canonical, final schema per supported backend. New installations create the complete current schema directly. Historical incremental database upgrades remain unsupported.

## Customer identity contract

Customer identity is split into an internal relational key and a public Capivara code.

- `customers.id`: internal numeric primary key.
- `customers.customer_code`: public immutable identifier in the form `CLI-000001`.
- `dashboard_users.username`: login identity and never a Customer primary key.
- Customer-facing APIs, dashboard search and billing may expose/use `customer_code`; relational foreign keys use `customers.id`.

The public code is derived from the numeric key and is never accepted from an administrator during Customer creation.

Examples:

| id | customer_code | name |
|---:|---|---|
| 1 | CLI-000001 | Aurora |
| 2 | CLI-000002 | Example Hosting |
| 17 | CLI-000017 | Customer 17 |

Deleted numeric keys are not reused. Consequently, deleted public Customer codes are not reused.

## Canonical Customer table

### PostgreSQL

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_code TEXT GENERATED ALWAYS AS (
        'CLI-' || LPAD(id::TEXT, 6, '0')
    ) STORED UNIQUE,
    controller_id TEXT NOT NULL,
    name TEXT NOT NULL,
    legal_name TEXT,
    email TEXT,
    phone TEXT,
    document_type TEXT CHECK (
        document_type IS NULL OR document_type IN ('cpf', 'cnpj', 'other')
    ),
    document_number TEXT,
    account_email TEXT,
    sftp_username TEXT,
    status TEXT NOT NULL DEFAULT 'active' CHECK (
        status IN ('active', 'suspended', 'cancelled')
    ),
    registration_status TEXT NOT NULL DEFAULT 'managed' CHECK (
        registration_status IN ('managed', 'pending', 'active', 'disabled')
    ),
    email_verified_at TIMESTAMPTZ,
    billing_provider TEXT,
    billing_customer_id TEXT,
    billing_status TEXT,
    billing_synced_at TIMESTAMPTZ,
    metadata_json JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_customers_controller
        FOREIGN KEY (controller_id)
        REFERENCES controllers(id)
        ON DELETE RESTRICT
);
```

The other backends must implement the same logical contract. Where generated stored columns are not sufficiently portable, `customer_code` may be persisted by the repository immediately after obtaining the generated numeric key, with a unique constraint enforcing the same external contract.

## Foreign-key contract

Every relational Customer reference becomes numeric and references `customers(id)`:

- `instances.customer_id`
- `service_contracts.customer_id`
- `customer_account_members.customer_id`
- `customer_invitations.customer_id`
- any later table that owns a Customer reference

`dashboard_users.scope_id` currently also carries Customer identity. Baseline v2 must stop treating it as an untyped text foreign key. The preferred target is a dedicated numeric Customer scope reference while retaining non-Customer scopes without overloading the Customer PK. Until that refactor is complete, repositories must resolve `customer_code` to the numeric Customer key at their boundary rather than placing `CLI-*` in relational foreign keys.

## Deletion contract

Customer deletion is an application lifecycle operation, not a raw `DELETE customers` shortcut.

1. Instances are placed into the existing Agent-confirmed removal lifecycle.
2. Physical instance materialization is confirmed absent.
3. Instance-dependent rows are removed according to their FK policy.
4. Contracts, memberships, invitations and Customer-owned records are removed.
5. The Customer row is removed.

Customer-owned records with no independent lifecycle should prefer `ON DELETE CASCADE`. Instances must not rely on a Customer cascade because deleting their database row before Agent cleanup can orphan a live game server.

## Baseline schema policy

The files below are authoritative complete-schema snapshots, not migration histories:

- `database/schemas/postgresql.sql`
- `database/schemas/sqlite.sql`
- `database/schemas/mysql.sql`
- `database/schemas/mariadb.sql`

They must not contain historical markers such as `source: 003_...`, `Migration 014`, or a chain of `ALTER TABLE` statements whose only purpose is reconstructing an old release sequence. A table should be declared once in its final form whenever dependency ordering permits it.

`dsm database init` applies the complete backend schema to an empty database. `dsm database migrate` remains only an idempotent schema-validation alias and does not support upgrading historical database layouts.

## Implementation sequence

1. Introduce the numeric Customer identity contract and Customer-code helpers.
2. Rebuild Customer-related definitions in all four canonical schemas.
3. Convert all Customer foreign keys to numeric keys.
4. Update repositories to accept public Customer codes at external boundaries and resolve them internally.
5. Remove the editable Customer ID field from the Dashboard and API create payloads.
6. Rebuild all four schema files as clean final snapshots with no historical migration narrative.
7. Update schema parity checks and tests for PostgreSQL, SQLite, MySQL and MariaDB.
8. Validate a clean install and the full Customer -> Contract -> Instance lifecycle.

## Compatibility policy

Baseline v2 intentionally does not preserve historical Customer rows or old Customer primary-key values. This project stage permits recreating the database for the new baseline. Code must therefore avoid adding compatibility migrations whose sole purpose is transforming the old textual Customer PK into the new numeric model.
