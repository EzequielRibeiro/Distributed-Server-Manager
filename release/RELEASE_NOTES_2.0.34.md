# Capivara DSM 2.0.34

Patch release after Capivara DSM 2.0.33 to roll out the final provisioning-alert idempotency fix and Hybrid Agent parity fixes validated on the current main branch.

## Provisioning failure alert reliability

- Make provisioning-failure alerts idempotent per instance so a previous active failure alert cannot abort the Hybrid provisioning worker with a uniqueness violation.
- Keep alert publication isolated from provisioning state/result application so observability failures cannot stop the provisioning command loop.
- Serialize PostgreSQL `datetime`/`date` values correctly in `cap alerts active`, `history` and `get` JSON output.

## Hybrid Agent parity

- Make `cap agent health` use the embedded Hybrid transport instead of probing the local Controller through HTTP `/ping`.
- Report Hybrid health with the canonical `embedded-database` transport and require the embedded Agent/Node identity to be complete.
- Stop Infrastructure Doctor from emitting the false `agent_missing_credential` finding for an Agent whose authoritative persisted Node role is `hybrid`.
- Preserve standalone/remote Agent behavior: HTTP Controller health probing and active permanent credentials remain required.

## Regression protection

- Cover Hybrid health without `/ping` and standalone health with the normal Controller probe.
- Cover credential requirements for `agent`, `hybrid`, missing and unknown Node roles with fail-closed behavior outside Hybrid.
- Preserve the existing provisioning failure alert uniqueness constraint rather than weakening database protection.

## Release scope

This release contains the changes merged after `v2.0.33`:

- #406 — `fix(provisioning): make failure alerts idempotent`
- #407 — `fix: restore Hybrid health and doctor credential parity`

Release artifacts, SHA256 checksums and manifests are generated by the canonical repository Release workflow for DSM and standalone Linux/Windows Agents.
