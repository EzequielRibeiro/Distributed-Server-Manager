# Capivara DSM 2.0.33

Hotfix release for provisioning-failure alert persistence after Capivara DSM 2.0.32.

## Provisioning failure alerts

- Fix CRITICAL provisioning-failure alerts failing to persist because the Alert Store received the non-canonical uppercase scope `INSTANCE`.
- Use the canonical lowercase instance scope required by the alert schema while preserving existing instance/controller ownership validation.
- Keep the rich provisioning diagnostic behavior introduced in 2.0.32: failed progress capped at 99%, correlation id, stage, Agent/node, customer/game context, exception type, sanitized error, failure timestamp and Admin-only sanitized traceback.
- Preserve provisioning-id based alert deduplication.

## Regression protection

- Add a dedicated `Provisioning Failure Alert Gate` that executes the rich provisioning diagnostics and alert regression suite.
- Validate CRITICAL alert creation and deduplication in addition to RBAC, sanitization and failure-progress semantics.

## Real E2E evidence

The issue was reproduced on the Hybrid Controller `horizon-server` with Palworld provisioning operation `instance-provision-c60cd8aaef01421ea10eb7019893ac9a` after deploying 2.0.32. The operation correctly produced `failed`, `progress=99`, a critical Universal Event and Admin-only sanitized traceback, while `cap alerts active` remained empty. CI then reproduced the alert insertion failure as an alert-scope CHECK constraint violation.
